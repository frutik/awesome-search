Quepid proposals: plain-English questions, judge calibration, prompt auto-tuning

An open pull request, #1847, adds an MCP server to Quepid. With it, an assistant such as Claude or Cursor can answer plain-English questions about Quepid data, such as which searches scored worst in the last snapshot or whether one rater scores harsher than the others. It can also create cases, rate documents and share cases with a team. The server is off unless an administrator turns it on, uses existing personal API keys, and sees only what that key already allows. Asking Quepid questions in plain English explains why this version lives inside Quepid rather than beside it.

A second PR, #1849, sets out what could come next as three architecture decision records. Judge calibration, built in #1827, compares an AI judge with a human or LLM reference on a frozen sample. It reports Krippendorff's α and how the judge's grades change per-query nDCG@10. Auto-tuning would then rewrite the judge's prompt and choose few-shot examples, and the winning prompt would be tested against the original on held-out queries before anyone applies it. For this, the records recommend a small custom Ruby tuner over DSPy.rb or a separate Python GEPA service. “Relevance Factory” would let an external agent run all of this through the MCP server. All of it is still at the proposal stage, and none of the three PRs is merged.

BlitzRank: cheaper LLM reranking via tournament graphs

LLM reranking gets expensive when results are compared a pair at a time. BlitzRank, from Contextual AI, asks the LLM to order a small window and reads that answer as every pairwise preference inside it, infers more pairs by transitivity, and stops once the top ten are provably settled. Averaged over 14 TREC DL and BEIR datasets and two LLMs, it scored 56.9 nDCG@10 on 42k tokens per query, against 57.0 and 324k for a pairwise reranker. Doug Turnbull has pitched it as a search-evaluation judge, but the paper tests it only as a reranker and assumes noise-free judgments. Sourced from the paper.

MUVERA: multi-vector retrieval through one vector

Multi-vector models like ColBERT score with MaxSim, which ANN indexes can't search directly. MUVERA folds each document's token vectors into one fixed-dimensional encoding whose inner product approximates MaxSim, retrieves on that, then reranks with the real vectors. MUVERA now covers the Google paper's construction and its comparison with PLAID: Recall@k 10% higher and latency 90% lower on average over six BEIR datasets, with no win on MS MARCO. It also covers implementations in Weaviate Vector DB, Qdrant Vector DB via FastEmbed, and an OpenSearch plugin. Its benchmarks on three small corpora keep 87–97% of exact quality after rerank; Elastic's approach, average vectors, keeps 28–52%. All figures are the authors' own.

Click residuals for finding underperforming queries

When a query gets plenty of searches but few clicks, click residual puts a number on the shortfall: actual clicks minus attempts × the site's average CTR. Ranking queries by residual brings high-impact failures to the top, where a plain low-CTR list would bury them in the long tail. Clicks Residual now covers Walter Underwood's original definition with his Netflix cases. It also covers Charlie Hull's e-commerce extensions: per-category CTR baselines, exit rate and business value for prioritising, and query clustering to catch whole failing families such as misspellings. The metric shows that a query fails, not why. Sourced from Underwood's 2022 blog post and Click Residuals - A Clever Way to Find Underperforming Queries.

Corrections

  • Click Residual - A Query Success Metric credited the metric to "Ted Underwood" and linked a dead Medium URL. It is by Walter Underwood, published on his own blog in 2022.
  • That note's position-discounted formula and "running shoes" example are not in the source. It now gives Underwood's exp = att × ctr, res = clk − exp.
  • Search Observability called click residual "position-bias corrected". It uses a single average CTR baseline.
